## Общее

Базовый адрес — домен сервиса (`https://money.burninghouse.ru` в проде,
`http://localhost:8787` локально). Все пути ниже — относительно него.

Каждый запрос (кроме `/config` и `/health`) требует access-токен BurningHouse Auth:

```
Authorization: Bearer <access_token>
```

Токен подписан сервисом `auth.burninghouse.ru`, проверяется этим сервером локально по
JWKS. Живёт 15 минут — обновление токена (`grant_type=refresh_token`) на стороне
вызывающего, сюда не относится.

Данными пользователя владеет он сам: всё, что возвращают и принимают эндпоинты ниже —
привязано к `user_id` из токена (claim `sub`), у чужого токена — чужие данные, и никак иначе.

## Ошибки

Единый формат:

```json
{ "error": { "code": "validation_error", "message": "Проверьте поля запроса", "fields": { "amount": "число ≥ 0" } } }
```

`fields` — только у `validation_error`, ключ = имя поля.

| HTTP | code | Когда |
|---|---|---|
| 400 | `invalid_json` / `invalid_body` | Тело запроса не парсится как JSON, либо не той формы |
| 401 | `unauthorized` | Нет токена, истёк, подпись не сходится |
| 404 | `not_found` | Ресурса с таким `id` нет (или он принадлежит другому пользователю) |
| 405 | `method_not_allowed` | Метод не поддерживается для пути |
| 422 | `validation_error` | Тело запроса распознано, но поля не проходят проверку |

## `GET /api/v1/config`

Без токена. Куда фронту идти за входом — чтобы адрес auth-сервиса не был зашит в статику.

```json
{ "authBase": "https://auth.burninghouse.ru", "clientId": "finance" }
```

## `GET /api/v1/health`

Без токена. `{ "ok": true }` — для докер-healthcheck и мониторинга.

## Сущности

Пять ресурсов устроены одинаково: `transactions`, `goals`, `debts`, `fixed-payments`,
`assets`. Везде ниже `<resource>` — один из этих путей.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/api/v1/<resource>` | Список **всех** объектов пользователя (без пагинации — на масштабе личных финансов одного человека список не настолько большой, чтобы она была нужна) |
| `POST` | `/api/v1/<resource>` | Создать. Тело — поля объекта (см. [модели](#модели-данных)); `id` необязателен — если не передан или уже занят другим, сервер сгенерирует сам. Ответ — `201` и созданный объект |
| `GET` | `/api/v1/<resource>/<id>` | Один объект |
| `PUT` | `/api/v1/<resource>/<id>` | Полная замена объекта (не частичный patch — присылайте все поля, отсутствующие возьмут значение по умолчанию) |
| `DELETE` | `/api/v1/<resource>/<id>` | Удалить. `{"ok": true}` |

Список — не `[...]`, а `{"items": [...]}` (так в будущем можно добавить метаданные
вроде курсора пагинации, не ломая форму ответа).

Пример — создать расход:

```bash
curl -X POST https://money.burninghouse.ru/api/v1/transactions \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"type":"exp","amount":450,"cat":"Продукты","date":"2026-08-03T12:00:00.000Z","note":"Пятёрочка"}'
```

```json
{ "id": "a1b2c3d4-…", "type": "exp", "cat": "Продукты", "amount": 450, "note": "Пятёрочка",
  "date": "2026-08-03T12:00:00.000Z", "fixedId": null, "refundFor": null, "cardId": null, "cardRepay": null, "piggyId": null, "assetId": null, "goalId": null, "debtRepay": null, "assetQty": null }
```

### Что сервер НЕ делает сам

Валидирует только форму (тип поля, диапазон) — не бизнес-логику, которая в приложении
живёт на клиенте. В частности:

- Создание транзакции с `cardId` **не увеличивает** `used` у соответствующей кредитки
  в `debts` — это отдельный `PUT /api/v1/debts/<id>`, который вызывающий делает сам
  (ровно так же, как сейчас делает сам фронтенд «Финансов»).
- `cat` не сверяется со списком категорий приложения — можно прислать что угодно
  непустое, интерфейс просто покажет как есть с эмодзи по умолчанию.
- Ссылки `fixedId`/`refundFor`/`cardId`/`cardRepay`/`piggyId`/`assetId`/`goalId`/`debtRepay`
  не проверяются на существование — висячая ссылка не вызовет ошибку ни при записи, ни при чтении.
- Транзакция с `assetId`/`goalId`/`debtRepay` **не увеличивает**/не уменьшает сумму у
  соответствующего актива/цели/долга — как и с `cardId` выше, это отдельный запрос
  к `PUT /api/v1/{assets,goals,debts}/<id>`.
- `goalId` — единственная из этих ссылок, что встречается у транзакций **обоих** типов:
  `type:"exp"` — пополнение цели, `type:"inc"` — снятие с неё. Оба варианта одинаково
  исключены из `summary`/аналитики (это перевод, а не расход/доход).
- `assetQty` не пересчитывается сервером из `amount`/цены актива — записывается как есть.
  Клиент сам решает, указывать перевод в актив в рублях или в штуках бумаг.
- `interestPortion` тоже не пересчитывается сервером (нет формулы амортизации на сервере) —
  клиент сам делит платёж на проценты/тело по ставке долга и присылает готовое число.
- Email-напоминания о `paymentDay` — отдельный серверный фоновый процесс (не HTTP API),
  включается/выключается per-долг через `notifyEmail`/`notifyDaysBefore`.

Если понадобится атомарно поменять несколько сущностей разом — либо несколько
запросов подряд (риск частичного успеха тот же, что у любого multi-request API),
либо `PUT /api/v1/state` целиком (см. ниже) — как это по-прежнему делает сам фронтенд.

## `GET/PUT /api/v1/settings`

Общие для аккаунта настройки — не список, единственный объект.

```json
{
  "monthlyIncome": 120000,
  "theme": "dark",
  "hideBalance": false,
  "fixedSkips": ["fixedId:2026-08:5"],
  "piggy": { "enabled": true, "mode": "smart", "amount": 3450 },
  "displayName": "Данил"
}
```

`PUT` — полная замена, как и у сущностей выше.

## `GET /api/v1/summary`

Посчитанная сводка — не нужно тянуть все транзакции, чтобы показать баланс где-то ещё
(например, в другом сервисе BurningHouse).

```json
{
  "balance": 84250.5,
  "incomeTotal": 310000,
  "expenseTotal": 225749.5,
  "assetsTotal": 50000,
  "debtsOwed": 23000,
  "piggyAmount": 3450,
  "netWorth": 114700.5
}
```

`balance` — реальные деньги на счету (покупка с кредитки его не двигает, только её
погашение); `incomeTotal`/`expenseTotal` — за всё время; `netWorth` — баланс + активы +
копилка − долги. Точные формулы — `computeSummary()` в `server.js`, зеркалят
`cashTxAmount()`/`render()` из `assets/app.js`.

## `GET/PUT /api/v1/state`

Всё сразу — тот же набор данных, что и все ресурсы выше, одним объектом. Так
продолжает синхронизироваться сам фронтенд «Финансов» (одним запросом на изменение,
не десятком). Другим сервисам, скорее всего, удобнее гранулярные ресурсы выше.

`GET` →

```json
{ "data": { "tx": [...], "goals": [...], "debts": [...], "fixed": [...], "assets": [...], "monthlyIncome": null, "theme": "light", "hideBalance": false, "fixedSkips": [], "piggy": {...}, "displayName": "" }, "updatedAt": 1785900000000 }
```

`PUT` — тело `{"data": {...тот же формат...}}` → **полностью заменяет** все сущности
пользователя (не merge). Ответ — `{"ok": true, "updatedAt": …}`.

## Модели данных

Поля, которых нет во входящем теле, получают значение по умолчанию (колонка
«умолч.»); лишние поля тела молча игнорируются.

### transaction

| Поле | Тип | Умолч. | Примечание |
|---|---|---|---|
| `type` | `"exp"` \| `"inc"` | — | обязательно |
| `amount` | число ≥ 0 | — | обязательно, округляется до копеек |
| `date` | ISO-строка | — | обязательно |
| `cat` | строка | `"Другое"` | |
| `note` | строка | `""` | |
| `fixedId` | строка \| null | `null` | привязка к обязательному платежу |
| `refundFor` | строка \| null | `null` | id расхода, на который этот доход — возврат |
| `cardId` | строка \| null | `null` | покупка/начисление процентов с кредитки |
| `cardRepay` | строка \| null | `null` | id кредитки, которую гасит эта операция |
| `piggyId` | строка \| null | `null` | авто-пополнение инвесткопилки |
| `assetId` | строка \| null | `null` | перевод со счёта в актив (категория `"Перевод в актив"`) |
| `goalId` | строка \| null | `null` | пополнение цели (`type:"exp"`) или снятие с неё (`type:"inc"`) |
| `debtRepay` | строка \| null | `null` | платёж по обычному кредиту/рассрочке (не кредитке — для той см. `cardRepay`) |
| `assetQty` | число > 0 \| null | `null` | у переводов в тикерный актив (`assetId`) — точное количество бумаг, если перевод указан в штуках, а не в рублях |
| `interestPortion` | число > 0 \| null | `null` | у платежа по кредиту (`debtRepay`) — часть суммы, ушедшая на проценты, а не в тело долга (считается только если у долга указана `rate`) |

### goal

| Поле | Тип | Умолч. |
|---|---|---|
| `name` | строка | `"Без названия"` |
| `target` | число > 0 | — обязательно |
| `saved` | число ≥ 0 | `0` |
| `emoji` | строка | `"🎯"` |

### debt

| Поле | Тип | Умолч. | Примечание |
|---|---|---|---|
| `kind` | `"card"` \| null | `null` | `"card"` — кредитка, иначе обычный кредит/рассрочка |
| `name` | строка | `"Без названия"` | |
| `emoji` | строка | `"💳"`/`"🏦"` | |
| `limit` | число ≥ 0 | `0` | только для `kind:"card"` |
| `used` | число ≥ 0 | `0` | только для `kind:"card"` |
| `total` | число ≥ 0 | `0` | только для обычного кредита |
| `remaining` | число ≥ 0 | `0` | только для обычного кредита |
| `monthly` | число ≥ 0 | `0` | только для обычного кредита |
| `loanType` | `"mortgage"`\|`"consumer"`\|`"auto"`\|`"installment"`\|`"other"`\|null | `null` | только для обычного кредита; чисто ярлык для отображения/группировки, на расчёты не влияет |
| `rate` | число > 0 \| null | `null` | только для обычного кредита; % годовых. Если указана — платежи (`debtRepay`) делятся на проценты/тело, появляется график/переплата/калькулятор досрочного погашения в приложении |
| `startDate` | ISO-строка \| null | `null` | только для обычного кредита; дата оформления |
| `paymentDay` | целое 1–31 \| null | `null` | только для обычного кредита; день месяца для напоминания |
| `notifyEmail` | boolean | `false` | только для обычного кредита; слать письмо-напоминание о платеже |
| `notifyDaysBefore` | целое ≥ 0 | `3` | только для обычного кредита; за сколько дней до `paymentDay` напомнить |
